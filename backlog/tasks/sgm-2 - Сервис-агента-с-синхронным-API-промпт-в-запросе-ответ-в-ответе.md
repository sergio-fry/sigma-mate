## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Следующий шаг после каркаса: агент живёт как сервис, а не как однократный запуск. Сервис поднимает pi-сессию агента developer, держит её открытой и принимает снаружи запросы: в запросе приходит промпт, в ответе того же запроса возвращается ответ агента. Транспорт - HTTP с JSON, это самый простой вариант для проверки; стриминг, очереди, уведомления и вебсокеты не делаем, их обсудим позже.

Поведение при новом запросе: агент не должен дожидаться конца текущей работы. Новый промпт прерывает текущую задачу в рамках этой же сессии, и агент отвечает на новый вопрос. Клиент прерванного запроса не должен зависать: он получает внятный ответ о том, что его работа прервана.

Сессия одна, поэтому запросы идут по одному, а не параллельно. Это согласуется с pi: одна сессия держит один поток работы, а текущий прогон можно отменить.

Задача - первое приближение к тому, что описано в замысле: снаружи видно, чем агент занят, и можно вклиниться со своим вопросом. Трекер, телеметрия и переписка между агентами сюда не входят.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Сервис запускается одной командой, поднимает pi-сессию агента developer и работает до остановки; адрес и порт видны при старте и настраиваются.
- [x] #2 Клиент отправляет промпт одним запросом и получает ответ агента в ответе этого же запроса.
- [x] #3 Если во время работы над промптом приходит новый, сервис прерывает текущий прогон и отвечает на новый промпт; клиент прерванного запроса получает внятный ответ о прерывании, а не зависание и не пустой ответ.
- [x] #4 В один момент сервис ведёт один прогон: параллельной обработки запросов нет.
- [x] #5 Если pi не запустился или сессия упала, клиент получает внятную ошибку с кодом, отличным от успешного, а сервис остаётся жив.
- [x] #6 README описывает запуск сервиса, адрес API, формат запроса и формат ответа.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Подключить webrick (~> 1.9) в Gemfile; сервис - bin/serve, один процесс: WEBrick на 127.0.0.1:4567 (адрес/порт через SM_HOST/SM_PORT или --host/--port, видны при старте).
2. lib/sigma_mate/coordinator.rb: держит pi-сессию (PiAgent.session как в bin/ask), обрабатывает запросы по одному. Новый промпт во время активного прогона: помечает текущий прогон прерванным, зовёт session.abort, ждёт завершения потока событий (ошибка с reason=aborted -> agent_settled), затем запускает новый прогон. Запросы не параллелятся (mutex + условная переменная).
3. HTTP API: POST /ask, тело {"prompt": "..."}. Ответ 200 {"status":"ok","answer":"..."}; прерванный запрос -> 200 {"status":"interrupted","detail":...} (ответ сразу, не зависание); пустой/битый промпт -> 400; pi умер/не поднялся -> 503 {"status":"error","detail":...}, сервис жив.
4. Ошибки PiAgent (BinaryNotFound/TransportClosed/CommandError) маппятся в 503 с понятным detail; сервис не падает.
5. Тесты: (a) unit-тесты Coordinator с фейковой сессией (поддержка abort, ошибка с reason aborted, agent_settled) - прерывание и последовательная обработка без сети и сокетов; (b) e2e-спека: bin/serve против фейкового pi (расширенная заглушка в spec/fake_pi.rb: задержка ответа + обработка abort) через localhost: проверка ok-ответа, прерывания (второй запрос во время первого), последовательности, ошибки при мёртвом pi.
6. README: запуск, переменные окружения/флаги, формат запроса/ответа, коды ответа.
7. Живой прогон на машине, запись факта в заметки задачи; сверка AC и DoD, финальное резюме.
<!-- SECTION:PLAN:END -->

## Implementation Notes

Прерывание: длинный запрос (чтение файлов) запущен, через 10 с пришёл второй - второй получил 200 ok за 1.9 с, первый сразу получил 200 {"status":"interrupted","detail":"Прогон прерван новым запросом"} без зависания. Остановка по SIGTERM - чистая. Автотесты: 16 examples, 0 failures (включая 12 по сервису/координатору против фейкового pi).
