Протокол поверх шины NATS (doc-2) для общения агентов sigma-mate и
оркестратора. Транспортная часть - подписка сервиса на очередь своего
идентификатора - сделана в SGM-4; этот документ задаёт смысл сообщений.
Реализация: сторона агента - SGM-6, сторона отправителя - SGM-7.

Метафора: почтовый ящик. У каждого агента есть уникальный идентификатор;
отправитель кладёт сообщение в его ящик, как письмо. Агент обрабатывает
сообщение как задачу в своей сессии (та же работа, что HTTP-запрос в
SGM-2, но асинхронно) и публикует в шину ответ: работа готова, вот
результат. Отправитель связывает ответ со своим сообщением, даже если
ответ пришёл намного позже.

## Адресация

- Идентификатор агента - UUID (каноническая форма: строчные буквы,
  дефисы). Он же - адрес агента в шине и токен темы. В идентификаторе
  запрещены точки, пробелы и NATS-подстановочные символы (`*`, `>`):
  тема собирается из идентификатора дословно.
- Одна живая копия агента на идентификатор: машина на сотрудника (doc-1),
  queue groups не используются.

### Темы протокола

Все темы протокола - в неймспейсе `sigma.`, чтобы не пересекаться со
служебными темами NATS (`$SYS`, `_INBOX`) и случайными подписками. Тема
читается слева направо: неймспейс, тип участника, его идентификатор,
канал. Каналов у агента два: входящие и события.

| Тема | Назначение | Режим |
|---|---|---|
| `sigma.agent.<идентификатор>.inbox` | входящие агенту: задачи и запросы | pub/sub, у агента постоянная подписка |
| `sigma.agent.<идентификатор>.events` | всё, что агент транслирует наружу: ответы и события телеметрии | pub/sub, публикует агент, слушает любой |
| `sigma.broadcast` | сообщение всем: объявления, вопросы в комнату | pub/sub, агенты подписаны с момента старта |

Ответ агенту (при переписке агент-агент) - обычный request в его inbox.
Ответ агента - событие в его events (см. «Корреляция»); телеметрия
(SGM-8) идёт туда же. Вилдкарды NATS работают как «слушаю всех»:
`sigma.agent.*.events` - события и ответы всех агентов одной подпиской,
`sigma.agent.<идентификатор>.>` - весь след одного агента, `sigma.>` -
весь трафик протокола.

## Конверт

Каждое сообщение протокола - один JSON-документ в UTF-8 (payload NATS-сообщения):

```json
{
  "proto": "sigma/1",
  "type": "request | reply | error | event",
  "id": "uuid сообщения, генерирует отправитель",
  "correlation_id": "uuid исходного request; в request - null",
  "from": "идентификатор отправителя",
  "to": "идентификатор получателя; для broadcast - *",
  "ts": "ISO 8601, UTC",
  "body": {}
}
```

Версия `proto` - строка `sigma/1`. Неизвестные поля игнорируются;
конверт с чужим `proto` отвечает ошибкой `bad_request`.

- **request** - задача или вопрос. Тело: `{"task": "<текст>"}`. Текст
  несёт тот же смысл, что `prompt` в HTTP `/ask`: агент выполняет его
  инструментами своей сессии.
- **reply** - работа по исходному сообщению завершена. Тело по статусу:
  - `{"status": "ok", "answer": "<результат>"}` - задача выполнена;
  - `{"status": "interrupted", "detail": "<что случилось>"}` - прогон
    вытеснен более новым сообщением (как HTTP `200 interrupted`);
  - `{"status": "error", "code": "<код>", "detail": "<описание>"}` -
    задача не выполнена.
- **error** - сообщение не принято к обработке (задача не начиналась).
  Тело: `{"code": "<код>", "detail": "<описание>"}`.

- **event** - событие телеметрии: то, что происходит в работе агента.
  Публикуется в events вместе с ответами, тело: `{"kind": "<вид>", ...}`;
  перечень видов ведёт SGM-8, этот документ их не фиксирует.

Коды ошибок: `bad_request` - конверт не разобран (битый JSON, чужой
proto, нет обязательных полей); `unavailable` - сессия агента не поднята
(аналог HTTP 503); `internal` - прочее. Коды - закрытый список, новые
добавляются правкой этого документа.

## Корреляция

- Отправитель генерирует уникальный `id` для каждого request.
- Ответ - событие в events-канале агента: конверт `reply` (или `error`) с
  `correlation_id`, равным `request.id`. Отправитель подписан на
  `sigma.agent.<идентификатор>.events` и закрывает ожидание первым
  событием с нужным `correlation_id`. Связь «запрос - ответ» определяется
  парой «агент + correlation_id», поэтому работает и когда ответ пришёл
  позже, и когда отправитель успел переподключиться к шине.
- Повторный ответ на тот же correlation_id отправитель игнорирует:
  первый ответ закрывает запрос. Дубликаты request возможны (после
  обрыва и републикации): протокол не вводит дедупликацию, повтор
  обрабатывается как обычный request.

## Занятый агент

**Решение: новое сообщение прерывает текущую работу.** Прерванному
отправителю уходит reply со `status: "interrupted"`, новое сообщение
выполняется. То же поведение, что у HTTP `/ask` (SGM-2): новое
вытесняет текущее.

Обоснование:

1. Правило «одна задача в моменте» (doc-1) запрещает параллельность, но
   не требует очереди. Оно же прямо разрешает переключение: «может
   переключиться на следующую».
2. Более новое сообщение отражает актуальную волю отправителя.
   Выполненное позже старое сообщение вредно: оно опиралось на контекст,
   который уже изменился (например, «делай вместо этого вот это»).
3. HTTP и шина - две точки входа в один и тот же Coordinator (одна
   сессия, одно правило вытеснения). Единое поведение - одна реализация,
   нет двух очередей с разной семантикой; SGM-6 сводится к ещё одному
   входу, а не к новой дисциплине исполнения.
4. Никто не теряется молча: вытесненный отправитель получает
   `interrupted` и сам решает - повторить, подождать или эскалировать.

## Таймауты, повторы, неизвестный адресат

- Агент обрабатывает задачу сколько нужно: протокол не ограничивает время
  прогона. Ограничения задаёт только отправитель.
- Отправитель ждёт ответ с таймаутом (по умолчанию 10 минут, задаётся при
  отправке). Таймаут истёк - отправитель фиксирует неудачу и может
  повторить: не более N попыток с паузой; в повторах допустим тот же `id`
  (та же задача) или новый - оба варианта корректны, дедупликации в
  протоколе нет.
- **Неизвестный адресат.** Core NATS не сообщает издателю, что у темы нет
  подписчиков: PUB без подписчика просто пропадает. Немедленного отказа в
  протоколе нет, единственный сигнал - таймаут отправителя. После
  исчерпания попыток отправитель сообщает наверх: «агент не ответил»
  (неизвестен / выключен / не успел - на этом уровне неразличимо;
  различить их позволит реестр живых агентов, он вне этого документа).
- **Офлайн-доставка не поддерживается.** Без JetStream (doc-2) подписка
  живёт, только пока жив агент: сообщения в пустой inbox пропадают. По
  замыслу (doc-1) оркестратор будит машину агента до отправки.
- Размер сообщения - до 1 MB (ограничение ноды, doc-2). Большие данные
  передаются ссылкой на файл, не телом сообщения.

## Отображение на NATS

- **Доставка задачи** - pub/sub: отправитель публикует конверт `request` в
  `sigma.agent.<идентификатор>.inbox`; агент (SGM-4) подписан постоянно.
- **Ответ** - pub/sub: агент публикует конверт `reply`/`error` в свой
  `sigma.agent.<идентификатор>.events` с `correlation_id` исходного
  запроса. Транспортный request/reply NATS и временные `_INBOX`-темы
  протоколом не используются: ответ - публичное событие агента, его
  слышат все подписчики (интерфейс, оркестратор, другие сотрудники), а
  адресат узнаёт свой ответ по `correlation_id`.
- **Синхронное ожидание** строится поверх: подписаться на events агента,
  отправить request в его inbox, ждать событие с нужным `correlation_id`
  до таймаута. Так работает CLI отправителя (SGM-7).
- **Broadcast** - `PUB sigma.broadcast`, конверт с `to: "*"`, ответ не
  ожидается по умолчанию; если объявление требует реакции, ответ -
  обычное событие `reply` в events отвечающего с `correlation_id`
  исходного сообщения.
- **Телеметрия** - конверты `event` в тот же events агента; подписчики
  читают всё подряд и разбирают по `kind`. Виды - SGM-8.

## Примеры потоков

1. **Ожидание с таймаутом (CLI SGM-7).** Подписка на
   `sigma.agent.B.events`; `PUB sigma.agent.B.inbox` request (`id: 42`,
   body `{"task": "прогони тесты"}`) - агент обрабатывает - `PUB
   sigma.agent.B.events` reply `{"correlation_id": "42", "status": "ok",
   "answer": "тесты зелёные"}`.
2. **Асинхронно.** Оркестратор публикует request (`id: 42`) и живёт
   дальше; когда агент закончит, в его подписке на
   `sigma.agent.B.events` появится reply с `correlation_id: 42` - хоть
   через час, хоть после переподключения к шине.
3. **Вытеснение.** Агент B занят задачей 42; приходит 43 - B публикует в
   `sigma.agent.B.events` reply по 42 со `status: "interrupted"` и
   выполняет 43.
4. **Ошибка.** Отправитель шлёт в `sigma.agent.C.inbox`, агента C нет;
   через таймаут и N попыток отправитель фиксирует «C не ответил» и
   эскалирует наверх.
