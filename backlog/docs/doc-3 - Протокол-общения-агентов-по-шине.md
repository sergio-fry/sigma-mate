# Протокол общения агентов по шине

Протокол поверх шины NATS (doc-2) для общения агентов sigma-mate и
оркестратора. Транспортная часть - подписка сервиса на очередь своего
идентификатора - сделана в SGM-4; этот документ задаёт смысл сообщений.
Реализация: сторона агента - SGM-6, сторона отправителя - SGM-7.

Метафора: почтовый ящик. У каждого агента есть уникальный идентификатор;
отправитель кладёт сообщение в его ящик, как письмо. Агент обрабатывает
сообщение как задачу в своей сессии (та же работа, что HTTP-запрос в
SGM-2, но асинхронно) и публикует в шину ответ: работа готова, вот
результат. Отправитель связывает ответ со своим сообщением, даже если
ответ пришёл намного позже.

## Адресация

- Идентификатор агента - UUID (каноническая форма: строчные буквы,
  дефисы). Он же - адрес агента в шине и токен темы. В идентификаторе
  запрещены точки, пробелы и NATS-подстановочные символы (`*`, `>`):
  тема собирается из идентификатора дословно.
- Одна живая копия агента на идентификатор: машина на сотрудника (doc-1),
  queue groups не используются.

### Темы протокола

Все темы протокола - в неймспейсе `sigma.`, чтобы не пересекаться со
служебными темами NATS (`$SYS`, `_INBOX`) и случайными подписками:

| Тема | Назначение | Режим |
|---|---|---|
| `sigma.agent.<идентификатор>` | очередь агента: входящие задачи | pub/sub, у агента постоянная подписка |
| `sigma.inbox.<идентификатор>` | почтовый ящик агента для ответов ему | pub/sub, подписка держится, сколько жив отправитель |
| `sigma.broadcast` | сообщение всем: объявления, вопросы в комнату | pub/sub, агенты подписаны с момента старта |
| `sigma.event.<идентификатор>` | события работы агента (телеметрия) | pub/sub, без корреляции; зарезервировано для SGM-8 |

`_INBOX.<nuid>` - транспортные временные темы request/reply самого NATS,
их можно использовать для синхронного ожидания, но протокол их не
назначает (см. «Отображение на NATS»).

## Конверт

Каждое сообщение протокола - один JSON-документ в UTF-8 (payload NATS-сообщения):

```json
{
  "proto": "sigma/1",
  "type": "request | reply | error",
  "id": "uuid сообщения, генерирует отправитель",
  "correlation_id": "uuid исходного request; в request - null",
  "from": "идентификатор отправителя",
  "to": "идентификатор получателя; для broadcast - *",
  "ts": "ISO 8601, UTC",
  "body": {}
}
```

Версия `proto` - строка `sigma/1`. Неизвестные поля игнорируются;
конверт с чужим `proto` отвечает ошибкой `bad_request`.

- **request** - задача или вопрос. Тело: `{"task": "<текст>"}`. Текст
  несёт тот же смысл, что `prompt` в HTTP `/ask`: агент выполняет его
  инструментами своей сессии.
- **reply** - работа по исходному сообщению завершена. Тело по статусу:
  - `{"status": "ok", "answer": "<результат>"}` - задача выполнена;
  - `{"status": "interrupted", "detail": "<что случилось>"}` - прогон
    вытеснен более новым сообщением (как HTTP `200 interrupted`);
  - `{"status": "error", "code": "<код>", "detail": "<описание>"}` -
    задача не выполнена.
- **error** - сообщение не принято к обработке (задача не начиналась).
  Тело: `{"code": "<код>", "detail": "<описание>"}`.

Коды ошибок: `bad_request` - конверт не разобран (битый JSON, чужой
proto, нет обязательных полей); `unavailable` - сессия агента не поднята
(аналог HTTP 503); `internal` - прочее. Коды - закрытый список, новые
добавляются правкой этого документа.

## Корреляция

- Отправитель генерирует уникальный `id` для каждого request.
- Ответ публикуется в reply-тему из транспорта (поле `reply` PUB-команды
  NATS), а `reply.correlation_id` равен `request.id`. Связь «запрос -
  ответ» определяется парой «reply-тема + correlation_id», поэтому
  работает и когда ответ пришёл позже, и когда отправитель успел
  переподключиться к шине.
- Повторный ответ на тот же correlation_id отправитель игнорирует:
  первый ответ закрывает запрос. Дубликаты request возможны (после
  обрыва и републикации): протокол не вводит дедупликацию, повтор
  обрабатывается как обычный request.

## Занятый агент

**Решение: новое сообщение прерывает текущую работу.** Прерванному
отправителю уходит reply со `status: "interrupted"`, новое сообщение
выполняется. То же поведение, что у HTTP `/ask` (SGM-2): новое
вытесняет текущее.

Обоснование:

1. Правило «одна задача в моменте» (doc-1) запрещает параллельность, но
   не требует очереди. Оно же прямо разрешает переключение: «может
   переключиться на следующую».
2. Более новое сообщение отражает актуальную волю отправителя.
   Выполненное позже старое сообщение вредно: оно опиралось на контекст,
   который уже изменился (например, «делай вместо этого вот это»).
3. HTTP и шина - две точки входа в один и тот же Coordinator (одна
   сессия, одно правило вытеснения). Единое поведение - одна реализация,
   нет двух очередей с разной семантикой; SGM-6 сводится к ещё одному
   входу, а не к новой дисциплине исполнения.
4. Никто не теряется молча: вытесненный отправитель получает
   `interrupted` и сам решает - повторить, подождать или эскалировать.

## Таймауты, повторы, неизвестный адресат

- Агент обрабатывает задачу сколько нужно: протокол не ограничивает
  время прогона. Ограничения задает только отправитель.
- Отправитель ждёт ответ с таймаутом (по умолчанию 10 минут, задаётся
  при отправке). Таймаут истёк - отправитель фиксирует неудачу и может
  повторить: не более N попыток с паузой; в повторах допустим тот же
  `id` (та же задача) или новый - оба варианта корректны, дедупликации
  в протоколе нет.
- **Неизвестный адресат.** Core NATS не сообщает издателю, что у темы
  нет подписчиков: PUB без подписчика просто пропадает. Немедленного
  отказа в протоколе нет, единственный сигнал - таймаут отправителя.
  После исчерпания попыток отправитель сообщает наверх: «агент не
  ответил» (неизвестен / выключен / не успел - на этом уровне
  неразличимо; различить их позволит реестр живых агентов, он вне этого
  документа).
- **Офлайн-доставка не поддерживается.** Без JetStream (doc-2) подписка
  живёт, только пока жив агент: сообщения в пустой ящик пропадают. По
  замыслу (doc-1) оркестратор будит машину агента до отправки.
- Размер сообщения - до 1 MB (ограничение ноды, doc-2). Большие данные
  передаются ссылкой на файл, не телом сообщения.

## Отображение на NATS

- **Доставка задачи** - pub/sub: отправитель делает `PUB
  sigma.agent.<id>` с reply-темой; агент (SGM-4) подписан постоянно.
- **Ответ** - тоже pub/sub: агент публикует конверт reply/error в
  reply-тему из полученного сообщения (`msg.reply`).
- **Синхронное ожидание** - request/reply NATS как есть: отправитель
  вызывает `nc.request(sigma.agent.<id>, конверт, timeout)`, клиент сам
  подписывается на временный `_INBOX.<nuid>` и он же - reply-тема
  PUB-команды. Семантика протокола не меняется: агент видит обычную
  reply-тему. Так работает CLI отправителя (SGM-7).
- **Асинхронное ожидание** - отправитель держит постоянную подписку на
  `sigma.inbox.<идентификатор>` и указывает её reply-темою: ответы
  находят его, когда угодно позже, независимо от соединений. Это
  «почтовый ящик» в чистом виде.
- **Broadcast** - `PUB sigma.broadcast`, конверт с `to: "*"`, ответ не
  ожидается по умолчанию; если объявление требует реакции, каждый
  отвечает в свой `sigma.inbox.<идентификатор>` - сама по себе тема
  broadcast безадресна.
- **События** - агент публикует `sigma.event.<идентификатор>`, подписчики
  читают, корреляции нет. Детали - SGM-8.

## Примеры потоков

1. **Синхронно (CLI SGM-7).** `PUB sigma.agent.B` (reply `_INBOX.x`,
   body `{"task": "прогони тесты"}`) - агент обрабатывает - `PUB
   _INBOX.x` reply `{"status": "ok", "answer": "тесты зелёные"}`.
2. **Асинхронно.** Отправитель A подписан на `sigma.inbox.A`; `PUB
   sigma.agent.B` (reply `sigma.inbox.A`, `id: 42`) - ответ приходит в
   `sigma.inbox.A` с `correlation_id: 42`, хоть через час; A узнаёт
   задачу 42 и закрывает ожидание.
3. **Вытеснение.** Агент B занят задачей 42; приходит 43 - B отвечает
   по 42 `{"status": "interrupted", ...}` и выполняет 43.
4. **Ошибка.** Отправитель шлёт в `sigma.agent.C`, агента C нет; через
   таймаут и N попыток отправитель фиксирует «C не ответил» и
   эскалирует наверх.
